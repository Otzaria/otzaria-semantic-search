# CI לעדכון וקטורים — תוכנית, ממצאים ומספרים

> 9 באוגוסט 2026. מסמך זה מחליף את סעיף 8 של `KAGGLE_FULL_VECTOR_BUILD_PLAN_HE.md`,
> שנכתב לפני שנקרא הקוד של הספרייה ושל ה־pipeline הקיים. כל מספר כאן נמדד וכל טענה על
> קוד מגובה במקום שבו הוא כתוב.

## 1. המספרים

| מדד | ערך |
|---|---:|
| מסמכים באינדקס ההפצה | 5,888,476 |
| ספרים | 7,288 |
| בניית האינדקס (כולל מיזוג ל־segment אחד) | ~90 שניות |
| וקטורים לשנייה, T4 בודד | **29.16** |

ההשוואה נעשתה על 23,972 וקטורים מטקסט אוצריא אמיתי, `build` מלא כולל אריזה ואימות.
**T4 מהיר פי 1.50 מ־P100**, כצפוי: מסלול ה־MMQ של llama.cpp דורש `__dp4a`, שמופיע
ב־compute capability 6.1, ול־P100 יש 6.0. בשני הכרטיסים `n_ctx` גדול יותר **מזיק** —
llama.cpp מקצה buffer ל־logits שה־backend הזה לעולם אינו קורא. ברירות המחדל בקוד,
`n_ctx=512` ו־batch 32, הן האופטימום ואין מה לכוונן.

זמן קיר = 28.0 ÷ (2 ריצות מקבילות × מספר חשבונות מאומתים): שני חשבונות ≈ 7 שעות,
חמישה ≈ 2.8 שעות.

## 2. הממצא שקובע את הארכיטקטורה

**וקטור הוא פונקציה של טקסט ה־embedding ותו לא.** אותו מודל, אותו backend, אותו מתכון
— אותו וקטור. לכן ה־ledger ממופתח על `embedding_text_sha256`, ולא על זהות שורה:

```
release חדש → אינדקס Tantivy → export-plan → digest לכל רשומה
  digest קיים ב־ledger הקודם → מעתיקים את הווקטור, אפס GPU
  digest חדש                 → נשלח ל־Kaggle
```

זה **מייתר את כל דיון המזהים היציבים**. מזהה הריצה שלנו,
`((catalogue_order + 1) << 32) + (ordinal + 1)`, הוא מיקומי וזז בכל שינוי בקטלוג — אבל
הוא תווית שמודבקת על הווקטור בסוף, לא המפתח שמאתר אותו.

והוא נכון גם במקום שבו זהות שורה הייתה **שוגה בשקט**: שורה שהטקסט שלה לא השתנה יכולה
לקבל טקסט embedding אחר אם שכנתה השתנתה והיא שואלת ממנה context. השוואה לפי מזהה
מפספסת את זה; השוואה לפי digest של הטקסט שבאמת מוטמע אינה יכולה לפספס.

## 3. מה נבדק בספרייה, ומה המסקנה

`lines_snapshot.db` (‏`DumpLines.kt:77-86`) הוא ארבע עמודות בלי מזהה, בלי PK ובלי UNIQUE:

```sql
CREATE TABLE lines_snapshot (
    source_name TEXT, canonical_he_title TEXT, line_index INTEGER, content TEXT )
```

`line_index` סידורי בתוך הספר; הוספת שורה מזיזה את כל מה שאחריה. מתוך ~16 השדות
שסעיף 8.3 ביקש, יש שם 4.

ל־`seforim.db` **כן** יש מזהה יציב אמיתי — `IdAllocator.lineId(bookId, sha1(content),
occurrenceIdx)`, נשמר ב־`build_state.db`, נזרע מנכס ה־release הקודם
`seforim.db.buildstate`. וקובצי `patch-v<from>-v<to>.db.zst` מפתחים `upsert_line` /
`delete_line` על אותו `line.id` (‏`PatchTables.kt:60`).

**המסקנה: אין מה לשנות בספרייה ואין מה לשנות ב־snapshot.** הזהות היציבה קיימת, היא
פשוט לא בדרך שלנו. אם בעתיד נרצה לצמצם אילו ספרים בכלל מעובדים מחדש, הוספת `l.id`,
`l.tocEntryId`, `l.heRef` ו־`b.id` ל־SELECT ב־`DumpLines.kt:113-127` היא שינוי של
שאילתה אחת וכל השדות כבר שם — **אופטימיזציה, לא תנאי.**

## 4. הקורפוס

האינדקס הקנוני נבנה ב־`otzaria build-release-index`, שמסנן PDF פעמיים
(‏`release_index_builder_cli.dart:170-173`, `indexing_repository.dart:218`). התוצאה:
שורות `seforim.db` בלבד. אינדקס חי של משתמש הכיל 6,032,249 מסמכים; ההפצה 5,888,476 —
143,773 מסמכים של PDF ותוספות מקומיות אינם בפנים.

לכן **אין צורך בגרסת מתכון חדשה** כדי לא להטמיע PDF: הכלל נאכף בבנייה. וחשוב מכך,
`corpus_id` מחושב מכל תוכן האינדקס, ולכן ה־CI חייב לצרוך את אותו אינדקס שהאפליקציה
מפיצה — לא לבנות אחד משלו.

## 5. הצינור

> **ה־workflow עצמו אינו בענף הזה.** הוא יושב ב־`vector-release-ci` עד שששת הפגמים
> שנמצאו בסקירה נסגרים — job שמניח קבצים מ־job אחר, העברת 28 GB ל־runner מתארח,
> `wait` שמסתיר כשל של כרטיס אחד, ותווית runner שאינה ייחודית. workflow על `main`
> נרשם ב־GitHub וניתן להפעלה, ולכן אחד שאינו יכול לרוץ מקצה לקצה אינו נכנס לשם.

```
repository_dispatch (PAT) מ־SeforimLibrary
  │
  ├─ plan      ubuntu-latest   אינדקס ההפצה → export-plan → 5.9M רשומות + digests
  │                            השוואה מול ה־ledger → reuse.jsonl + embed.jsonl
  ├─ embed     Kaggle GPU      רק ה־misses, מחולקים ל־shards
  ├─ assemble  self-hosted     וקטורים ממוחזרים + חדשים → pack → validate
  └─ publish   ubuntu-latest   ארטיפקט מלא + דלתא + ledger + digest חיצוני
```

`export-plan` ו־`embed-shard` כבר קיימים ונבדקו: build שנחתך לשלושה חלונות והורכב
מחדש מפיק אותו digest כמו build בתהליך אחד. גבול shard חייב ליפול על כפולה של גודל
ה־batch — פלט llama.cpp תלוי בהרכב ה־batch, ופיצול שחותך batch אינו משחזר.

שלושת השלבים שהיו חסרים — `ledger`, `plan-split` ו־`assemble` — קיימים עכשיו כתת־פקודות.

**ה־ledger נבנה אחרי האריזה ולא לפניה.** ‏`pack` ממיין את ה־payload לפי `semantic_id`,
ולכן הסדר ש־`assemble` מייצר אינו הסדר שמישהו מוריד. ledger שנבנה מן ה־assembler
פורסם פעם אחת וכל אחת מרשומותיו הצביעה על שורה אחרת — 20,000 מתוך 20,000 במדגם.
‏`ledger_from_artifact` קורא את `metadata.jsonl` של הארטיפקט ומצטרף אליו את
`records.jsonl` בשביל ה־digest המלא: ה־payload שומר `chunk_hash` של 32 תווים, שמספיק
להשוואה בזמן ריצה ואינו מספיק כדי להחליט מה לדלג עליו.

**ומיחזור מחייב `ledger-manifest.json`.** offsets ו־digests לבדם אינם אומרים מאיזה מודל
הווקטורים באו, ולכן ledger ממודל אחר היה נקלט בשקט לספרייה של שני מרחבים לא תואמים.
‏`plan-split` משווה כל שדה של `ModelIdentity` — כולל `pooling` ו־`max_tokens`, שנראים
קוסמטיים ואינם.

## 6. Kaggle

הדפוס שכבר עובד ב־`LinkerToOtzaria` הוא **הפוך** מדחיפת קרנל ותשאולו: הקרנל מאתחל
self-hosted JIT runner של GitHub Actions, ו־job רגיל רץ על ה־GPU. קלט ופלט זזים
כ־artifacts דרך `gh`. הסיבה מתועדת ב־`bootstrap.sh:9-10` — „big private datasets fail
Kaggle's processing, kernel outputs do not". נאמץ אותו.

הזדהות: **`KAGGLE_API_TOKEN` בלבד.** ‏`kaggle.json` עם `username`/`key` אינו נקרא
ב־CLI 2.2, ו־OAuth נשבר בפקיעה ובממשקי dataset.

**אימות טלפוני הוא תנאי, והוא בלתי נראה מן ה־API.** חשבון לא מאומת מדווח על 30 שעות
מלאות ואז מריץ בלי GPU ובלי רשת. `smoke.py` הוא הבדיקה: היא החזירה `gpus: []` לארבעה
חשבונות ושני T4 לחשבון מאומת, ולכן היא ראיה ולא כשל משותף.

התנגשות עם ה־linker אינה בעיה בתכנון הזה: ה־CI לוקטורים רץ בנפרד מהריצה השבועית ורק
אחרי שה־DB הסתיים. נשמור בכל זאת בדיקת preflight זולה שאין relink פעיל — היא עולה
קריאת API אחת ומחליפה התנגשות בכישלון מיידי.

## 7. מה שעוד פתוח

- **24 GB אינם נכנסים ל־runner מתארח.** ל־GitHub יש כ־14 GB פנויים; שלב ה־assemble
  צריך runner עצמי או הרכבה מפוצלת. זו החלטת תשתית, לא קוד.
- **גודל ההפצה.** 1024×f32 הם 24 GB למשתמש. משפחת Qwen3-Embedding מאומנת ב־MRL
  ותומכת בממדי פלט 32–1024, ולכן ממד קטן יותר וקוונטיזציה מתקבלים **מהווקטור המלא בלי
  לגעת ב־GPU**. לכן רצים עכשיו 1024×f32 כעותק אב ומכריעים אחר כך.
- **ה־ledger** הוא כ־5.9M שורות; נכס release שאינו נשלח למשתמש.
